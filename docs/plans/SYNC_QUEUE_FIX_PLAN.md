# 同步与队列整体修复计划

## 1. 范围与结论

本文是 SeedToCode 云同步的**未实施修复计划**。目标不是仅阻止「同名项目」这一种表象，而是把项目、文件、删除标记、学习进度、作业草稿与不可变提交在离线、重试、双设备及账号切换下的同步语义统一起来。

本计划不修改现有实现、不迁移数据库、不写入云端数据，也不改变本地优先的产品边界：同步不可用时，编辑、运行、学习和做题仍可在本地继续。

当前涉及的实现边界主要在：

- `web/js/sync-queue.js`：浏览器端待发送操作队列。
- `web/js/sync-engine.js`：拉取、推送、冲突与本地元数据协调。
- `web/js/cloud-client.js`：HTTP 错误分类与请求重试边界。
- `web/js/account-ui.js`、`web/js/app.js`：同步状态和项目名称的用户交互。
- `server/src/sync.ts`、`server/migrations/`：服务端身份、幂等、项目/文件写入与数据库约束。

## 2. 要解决的一组共同问题

这些问题具有同一根因：本地状态、待发送操作、远端版本与账号归属没有作为一个可恢复的整体建模。

1. 队列容量与丢失风险：现有队列有固定上限，达到上限时会直接截断较旧操作。对于删除标记、提交等不能重建的操作，这不能接受。
2. 同实体并发更新：某个项目或文件正在发送时再次编辑，旧操作失败后可能把较新的操作标为阻塞；旧确认也可能错误影响新状态。
3. 拉取与推送可并行：`pull` 与 `push` 各自有忙碌标记，但并未形成同一条串行流水线。滞后的拉取结果有机会覆盖较新的本地 revision 或映射。
4. 依赖关系没有显式表达：文件写入依赖项目已在云端存在；项目删除应压过其子文件写入。仅靠收到 `NOT_FOUND` 后补救，无法稳定处理离线与重试交错。
5. 重试与人工处理不清晰：目前主要是成功、重试、阻塞三类结果，缺少可识别的「需要处理」状态、可恢复依据和自动过期规则。
6. 账号切换后无法完整恢复：为防止越权上传而重置或搁置状态是正确方向，但队列、云端 ID 映射和同步元数据若不是按账号分桶，同一账号再次登录时无法可靠恢复原有待同步工作。
7. 同名规则前后端不一致：浏览器按 `trim().toLowerCase()` 判断，本地旧数据、离线创建、服务端原始名称唯一约束及数据库报错的语义并不完全一致。
8. 服务端错误没有产品化：数据库唯一约束等错误若未映射为稳定业务错误，客户端会把它当作暂时性服务器故障反复重试，既不能解决冲突，也会放大队列。
9. 可观察性不足：界面难以区分「已同步」「等待重试」「本地保留且不会上传」「需要解决」和「服务暂不可用」，用户无法安全判断项目是否真的上云。

## 3. 必须保持的约束

1. 不静默丢弃本地内容、删除标记或不可变提交。
2. 云端身份使用 `projectId`、`fileId` 等稳定 ID；项目名称只是一项受约束的显示属性，不能充当同步主键。
3. 不允许 revision、远端 ID 映射或已确认版本倒退。
4. 账号隔离 fail closed：上一账号、访客、归属未知的数据可以在本地读写，但未经明确并入前绝不能上传、云端运行或被另一账号看到。
5. 删除使用带 revision 的 tombstone；在获得确认前不得因队列整理而清除。
6. 作业提交、评分请求和其他不可变事件不能与普通状态写入一样合并或淘汰。
7. 同步失败不能阻止本地使用；恢复后应自动、有序、可解释地继续。
8. 新旧浏览器数据必须可迁移；迁移失败宁可保留为本地持有状态，也不能猜测归属或删除数据。

## 4. 目标数据模型

### 4.1 按账号分桶的持久化 Outbox

将通用的内存/单一队列升级为版本化的 `SyncQueue v2`。通过既有存储 facade 持久化，并以 `ownerId` 分区，而不是在账号切换时抹掉整份状态。

每个操作至少记录：

| 字段 | 含义 |
| --- | --- |
| `operationId` | 稳定幂等键；重试同一逻辑操作时不变。 |
| `ownerId` | 已确认的账号归属；访客或未知归属不进入可发送队列。 |
| `entityType` / `entityId` | `project`、`file`、`draft`、`progress`、`submission` 等实体身份。 |
| `kind` | 创建、更新、删除、提交等明确操作种类。 |
| `generation` | 同一实体每次状态变更递增，用于淘汰旧回调。 |
| `payload` 或安全引用 | 可恢复地重建请求；诊断日志不得输出代码或个人内容。 |
| `state` | `queued`、`in_flight`、`retry_at`、`needs_resolution`、`acknowledged`、`superseded`。 |
| `attempts` / `nextAttemptAt` | 退避、调度和用户可见重试时间。 |
| `dependsOn` | 父项目创建、删除屏障等前置关系。 |

队列分为两类，不能用同一套淘汰规则处理：

| 类别 | 例子 | 合并规则 | 清除条件 |
| --- | --- | --- | --- |
| 可折叠状态 | 项目名称、文件内容、草稿、阅读位置 | 同实体保留最新 generation；学习完成状态单调合并 | 最新 generation 获服务端确认，且无更新 generation |
| 不可变事件 | 作业提交、需要审计的交卷/成绩请求 | 永不按容量或同实体覆盖 | 服务端以 `operationId` 幂等确认，或明确进入可处理的失败状态 |

不再通过固定长度 `slice` 静默截断。容量压力应以可观测的存储配额状态暴露：优先压缩已确认记录和可折叠旧 generation；若仍无空间，暂停新增云端排队并明确提示，但保留本地编辑结果。

### 4.2 Generation 与陈旧回调防护

同一实体每一次可同步状态变化获得递增 generation。发送请求携带该 generation（或等价的本地序列），处理响应时必须验证：

- 成功只确认该 generation；如果已出现更新 generation，旧成功仅可作为历史确认，不能清除新操作。
- 旧请求失败不能把更新 generation 标成阻塞或需要处理。
- `needs_resolution` 记录也绑定 generation；后续更高 generation 已成功确认时，自动使旧记录 `superseded`。
- tombstone 是实体状态的一种更高优先级 generation；项目删除后，所有未确认的子文件写入自动 supersede。

这样可消除「发送中再次编辑，旧失败反而覆盖新状态」的竞态。

### 4.3 账号归属与持有状态

本地项目、文件、队列记录和云端 ID 映射必须都有明确归属：`ownerId`、`guest` 或 `unknown`。

- 已登录账号只加载和发送自己的分桶；退出/换号不删除该分桶，重新登录同一账号后可恢复。
- `guest` 数据只能通过显式、可预览的并入流程进入当前账号；并入前保持本地可用、云端不可见。
- `unknown` 或上一账号的数据保持 `held`，任何自动同步、自动云端运行和后台重试都跳过。
- 账号切换时清理的是会话内工作引用和请求，不是另一个账号的持久化 outbox。

## 5. 同步协调器

将独立的 `pulling`、`busy` 流程收敛为每个账号一个串行 `SyncSessionCoordinator`。手动同步、网络恢复、页面重开和定时重试都进入同一调度器，避免拉取和推送互相覆盖。

一次同步回合按下列顺序执行：

```text
确认账号与 ownership
  -> 从本地收集并持久化新 generation
  -> 拉取远端增量并按 revision/映射合并
  -> 计算依赖有向图
  -> 按依赖推送可发送操作
  -> 原子写回确认、映射、下一次重试时间与界面摘要
```

关键规则：

1. 所有会写同步元数据的流程都受同一 mutex 保护；网络请求可在锁外等待，但提交结果时必须重新检查 session epoch、账号和 generation。
2. 项目创建/恢复先于其文件写入；项目删除形成删除屏障，压过尚未发送的子文件写入。
3. 远端 ID、revision 和内容 hash 采用单调合并；过期响应不得回写较旧数值。
4. 拉取遇到本地未确认编辑时，保留本地内容并创建明确的云端副本/冲突材料，绝不直接覆盖本地。
5. 重试使用指数退避、抖动和最近 `nextAttemptAt` 定时器；不再只依赖固定间隔扫描。认证失效、配额不足、名称冲突等非瞬时错误不自动高频重试。
6. 账号变更或 session epoch 改变后，旧请求结果一律丢弃，不得写入当前会话。

## 6. 项目名称的统一策略

### 6.1 规范化键

增加仅用于比较与唯一约束的 `nameKey`，与保留给用户显示的 `name` 分离。规范应在浏览器、Worker 和迁移脚本共享或通过同一组可验证测试约束：

1. Unicode NFKC 规范化。
2. 去除首尾空白，并将连续普通空白压缩为一个空格。
3. 使用 Unicode 大小写折叠，而非仅 ASCII `toLowerCase()`。
4. 拒绝控制字符、零宽格式字符和规范化后为空的名称。
5. 保留原始显示名称（经安全清理），但唯一性以 `ownerId + nameKey` 判断。

名称不是同步 ID；所有项目匹配、文件归属与重试仍只使用项目稳定 ID。

### 6.2 冲突处理

- 在线新建：客户端预检仅改善体验，服务端 `nameKey` 唯一约束才是最终裁决。
- 离线新建后发生同名冲突：保留项目内容和本地 ID，为新建的本地项目生成确定且可见的可用后缀，例如「我的项目 (2)」，然后以新 generation 重试。不得删除、合并或覆盖任一项目。
- 已存在项目的改名冲突：不静默改名；进入 `needs_resolution`，显示本地名称和占用名称，用户可另选名称后继续。
- 旧本地数据：升级时检测同一归属下的规范化重名，保留全部项目，按稳定排序仅给后续项目追加后缀，并记录迁移来源以便诊断。
- 服务端：将数据库唯一约束违反映射为稳定的 `PROJECT_NAME_CONFLICT`，包含可安全展示的冲突信息，不把原始 SQLite 错误传给浏览器。

## 7. 服务端与数据库方案

### 7.1 API 边界

1. 每个会改变同步状态的端点继续验证会话和 `ownerId`，并接受/保存幂等键。
2. 对已处理的同一 `operationId` 返回同一语义结果，避免网络响应丢失时生成重复项目或重复提交。
3. 明确区分并返回：`UNAUTHENTICATED`、`FORBIDDEN`、`NOT_FOUND`、`REVISION_CONFLICT`、`PROJECT_NAME_CONFLICT`、`RATE_LIMITED`、`CAPACITY_EXCEEDED` 与临时 `SERVER_ERROR`。
4. 子资源请求只依据授权的稳定项目 ID；拒绝用名称回退匹配其他项目。
5. 删除和更新必须比较 revision，服务端返回可合并的当前版本或冲突材料，而不是悄悄接受过期写入。

### 7.2 新迁移（仅追加）

实施时新增顺序 migration，绝不改写已应用 migration。预期步骤：

1. 先部署可同时读取旧/新列的 Worker 代码，暂停受影响写入或启用维护开关。
2. 新增 `name_key` 列及必要的操作幂等记录表/索引。
3. 用与应用相同的规范化逻辑回填 `name_key`，先报告每个账号内的冲突，不自动丢弃行。
4. 对历史冲突做可审计的确定性改名或人工处理；确认无冲突后建立 `(owner_id, name_key)` 的部分唯一索引（排除 tombstone）。
5. 在真实远端 D1 验证 migration 可执行、索引存在、唯一约束和错误映射均正常后，才解除写入限制。

迁移、回填和生产验证必须分开记录；本地 D1 或 `--dry-run` 不等同于远端完成。

### 7.3 实施时不可跳过的风险控制

1. **本地原子性**：队列记录、同步元数据、远端 ID 映射和确认结果不能靠多份独立 `localStorage` key 的写入顺序维持一致。必须放进同一份可恢复状态，或通过 IndexedDB transaction 一起提交；崩溃在任意写入点都只能留下可重放/`held` 的状态。
2. **多标签页**：每个页面自己的 mutex 不能阻止另一标签页同时 pull/push。必须采用跨标签协调（例如带租约的单写入者加 `BroadcastChannel` 通知），或让每次提交都以持久化 generation/epoch 再校验；关闭、休眠和租约过期不能让旧标签页重新写回结果。
3. **名称规范的一致性**：浏览器、Worker、迁移脚本必须对同一组 Unicode 测试向量产生完全相同的 `nameKey`。不得依赖设备区域设置的大小写转换；规范化实现或测试向量必须与 migration 一起发布。
4. **离线后缀仍会冲突**：两台设备都可能选择同一个「(2)」。服务端仍是最终裁决；客户端收到再次冲突时必须重新计算可用名称或转入 `needs_resolution`，不能假设一次自动后缀必然成功。
5. **删除后的新意图**：删除屏障只压过删除之前的子文件写入。删除后又编辑、撤销或恢复必须成为明确的新 generation（必要时是新项目 ID），不能被旧 tombstone 一并 supersede。当前没有恢复 API 时，验收只能验证「删除后新建」；若要恢复原项目，需先单独定义恢复端点及其 revision 语义。
6. **已有能力不回退**：现有 `operationId` 幂等、revision 条件写、tombstone 与 `hold` 账号隔离是迁移基线。阶段 D 是补齐稳定错误码和名称语义，不是删除或重做这些既有保护。

## 8. 用户界面与恢复路径

同步入口应展示准确的账号范围和状态，而不把「同步失败」统称为一个模糊错误：

| 用户可见状态 | 含义 | 可用操作 |
| --- | --- | --- |
| 已同步 | 当前可折叠状态已由云端确认 | 查看最近同步时间 |
| 正在同步/已排队 | 已持久化，等待依赖、网络或计划重试 | 查看下一次尝试、立即重试 |
| 仅本地保留 | `guest`、`unknown` 或另一账号数据，保证不上传 | 查看归属说明、显式并入（仅 guest） |
| 需要解决 | 名称、revision 或无法自动合并的冲突 | 重命名、查看云端副本、保留两份 |
| 服务受限 | 认证、容量、频率限制或存储配额问题 | 登录、释放空间、稍后重试 |

界面只显示安全元数据和下一步，不显示文件内容、会话信息或底层数据库错误。实施任何 `web/` 改动前完整阅读 `FRONTEND_RULES.md`，并以现有应用内控件实现操作；状态更新不得引起无关布局跳动，窄屏也需实测。

## 9. 实施分期

### 阶段 A：冻结契约与建立测试入口

1. 为队列、协调器、名称规范化、服务器错误映射建立可独立测试的纯逻辑层。
2. 记录现有本地存储版本、队列字段、服务端 API 契约和已知兼容数据形态。
3. 先增加覆盖现有行为的回归测试，再替换实现，避免把当前本地优先、`operationId` 幂等、revision/tombstone 与 `hold` 安全边界回归掉。
4. 为崩溃在本地状态提交中间、多标签页同时运行、名称规范化和删除后的新意图建立可重复的测试入口。

### 阶段 B：实现 `SyncQueue v2`

1. 引入按账号分桶、版本化 schema、operationId、generation 和依赖字段。
2. 实现可折叠状态与不可变事件的分流，删除静默截断逻辑。
3. 使用单一可恢复持久化记录或 IndexedDB transaction 实现队列、元数据和确认状态的原子提交；不得依赖多个 key 的写入先后。
4. 实现持久化、升级、崩溃恢复、旧 generation supersede 和 tombstone 保留。
5. 保持旧队列只读迁移：迁移失败的记录进入 `held`/可诊断状态，不删除。

### 阶段 C：实现协调器与调度

1. 收敛 pull、push、手动同步、网络恢复和计时重试入口。
2. 实现 session epoch、账号切换取消、单调 revision 合并和依赖拓扑排序。
3. 引入最近重试时间定时器、退避和抖动；针对认证/冲突/配额错误停止无意义重试。
4. 明确跨标签页单写入者/租约与通知机制；每次网络响应写回前仍校验账号、session epoch 与 generation。

### 阶段 D：补齐服务端语义

1. 保留已有幂等写入与 revision 条件写，并补齐稳定错误码处理。
2. 完成 `nameKey` 的应用层校验与追加 migration。
3. 将约束冲突、revision 冲突和依赖缺失转成客户端可处理的业务响应。

### 阶段 E：名称、恢复 UI 与可观察性

1. 接入统一名称预检与离线新建自动后缀策略。
2. 为改名冲突和内容冲突提供 `needs_resolution` 操作。
3. 显示分桶、队列状态、下一次重试和只本地保留原因；所有诊断数据脱敏。

### 阶段 F：灰度与清理

1. 先让新代码能读取旧状态，再迁移写入；保留可回滚的旧解析器直至稳定期结束。
2. 小范围验证账号切换、离线编辑、双设备、删除后新建（以及另有定义时的显式恢复）和命名冲突后，再逐步启用新的数据库唯一约束与 UI。
3. 监控冲突率、重试深度、超时、存储配额和 `needs_resolution` 存量；只有确认无待迁移记录后才移除兼容路径。

## 10. 验收矩阵

| 场景 | 应验证的结果 |
| --- | --- |
| 同一文件发送中再次编辑 | 旧成功/失败不能确认、阻塞或清除新 generation。 |
| 请求到达但响应丢失 | 重试同一 `operationId`，服务端结果幂等，不生成重复资源。 |
| 拉取与本地编辑交错 | revision 不倒退；本地未确认内容被保留，冲突可见。 |
| 页面在队列/元数据写回中崩溃 | 重开后状态可恢复或进入 `held`，不出现已确认映射与待发操作互相矛盾的半写入。 |
| 同账号两个标签页同时同步 | 每个实体只按一个有效 generation 提交；旧标签页、过期租约或滞后响应不能回写新状态。 |
| 项目创建后立即写文件 | 文件等待项目创建确认或使用稳定依赖，不因短暂 `NOT_FOUND` 进入循环。 |
| 项目删除与文件更新交错 | 删除 tombstone 优先，删除前的子文件旧操作被 supersede；删除后的明确新意图不被吞掉。 |
| 队列超过旧容量 | 没有静默丢弃；状态合并可解释，不可变事件保留。 |
| 账号 A → B → A | B 永不发送 A 的数据；A 返回后可恢复 A 自己的队列与映射。 |
| 访客数据登录 | 未明确并入不上传；明确并入后仅上传用户选择的数据。 |
| 双设备离线同名新建 | 两份项目和内容都保留；即使自动后缀再次碰撞，服务端最终裁决后仍能重试或转入 `needs_resolution`。 |
| 已有项目同名改名 | 不静默改名，进入可操作的 `needs_resolution`。 |
| 删除后重建同名 | tombstone 和新项目 ID 不混淆；唯一约束只作用于活动项目。 |
| Unicode/空白变体项目名 | 浏览器、Worker 与迁移脚本生成相同 `nameKey`；历史冲突只报告/处理，不丢项目。 |
| 服务端约束/配额/认证失败 | 客户端显示正确状态，非瞬时错误不高频重试。 |

验证层级包括：队列与合并单元测试、Worker/D1 集成测试、真实浏览器的断网/重连与账号切换链路、以及所有受影响 `web/` 页面在桌面和窄屏下的几何稳定性检查。涉及 Worker 时至少运行服务端类型检查和对应本地 API 链路；涉及共享浏览器产物时按实际源码边界重建并提交产物；生产 migration 另行获得授权后才可执行与验证。

## 11. 明确不做的事

1. 不按名称自动合并两个不同项目，也不因重名删除任何一个项目。
2. 不为「看起来更方便」而放宽账号归属检查或跨账号自动上传。
3. 不把本地同步失败等同于本地文件损坏；本地内容始终优先保留。
4. 不把临时网络故障伪装成永久冲突，也不把永久业务错误无限重试。
5. 不在本计划阶段修改生产 D1、部署 Worker 或更改用户数据。
