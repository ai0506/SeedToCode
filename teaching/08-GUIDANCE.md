# 指导提示（guidance）

版本：1.3

## 1. 这是什么

编译器和指导者面对同一段错代码，说的话不一样：

| | 它回答的问题 | 例子 |
|---|---|---|
| **编译器** | 这里为什么不合法 | 「无法识别的字符 `，`」「找不到名称 `LENGHT` 的声明」「语句末尾出现意外内容：`lives`」 |
| **指导者** | 你多半想做什么、为什么没做到、怎么改 | 「这是中文输入法打出的逗号，切到英文半角」「你想写 `LENGTH` 吗」「`OUTPUT` 的多个值之间要用逗号分隔；要显示的文字要放进双引号里」 |

**指导提示**指的就是后一种。它不是一个新的严重等级（三级仍是阻断错误 / CAIE 规范 / 建议），而是**一种说话的立场**：不满足于指出「这里不合法」，要说出**可能的原因**和**更具体的那一处**。

方向是**更细、更具体，不是更专业、更笼统**。

## 2. 和「不写易错点」不矛盾

[02-CONTENT_SPEC.md](02-CONTENT_SPEC.md) 2.1 禁止在教学正文里写「常见错误是……」。指导提示不受这条约束，因为两者的依据不同：

| | 对谁说的 | 依据 | 结论 |
|---|---|---|---|
| 正文写「学生常忘记改条件变量」 | 所有人 | 猜的 | 禁止 |
| 提示说「第 3 行用了中文全角逗号 `，`」 | 这一份代码 | 看到的 | 鼓励 |

一个是对人群的**猜测**，一个是对眼前这段代码的**观察**。

这类错误的共同点：**对新手极难自查，对系统极易识别**——正是该由系统兜住的部分。新手盯着 `outpit "x"` 看十遍也看不出少了个 `u`，机器一眼就知道。

## 3. 现在有哪些

分散在三处，因为它们介入的时机不同。

### 3.1 静态分析时（`packages/language/src/` 的 `tokenizer` / `parser` / `checker` / `analyzer`）

**（a）从别的语言带过来的写法。** 这类代码在 Python、Java 里是对的，在伪代码里不是；报「不合法」不如直接说「在这里该怎么写」。

| 规则 | 触发 | 说给学生的话 |
|---|---|---|
| `type.arithmetic.stringPlus` | `+` 的任一边是 `STRING` / `CHAR` | 把两段文字接起来要用 `&`，不是 `+`。`+` 只做加法，例如 `OUTPUT "Hi " & Name` |
| `parser.relation.doubleEquals`（OP-003） | 紧挨着的两个 `=` | 比较只用一个 `=`，不是 `==` |
| `parser.input.promptNotAllowed`（IO-001） | `INPUT` 后面紧跟着字符串 | `INPUT` 后面只写要读进来的变量。提示语要单独写成上一行：`OUTPUT "Enter name"` |
| `literal.char.looksLikeString`（LIT-003） | 单引号里不止一个字符 | 单引号里只能放一个字符。要写一段文字请改用双引号 |
| `parser.declare.oneNamePerStatement`（DECL-003） | `DECLARE` 的名字后面跟着逗号 | 一句 `DECLARE` 只声明一个名字。要声明几个变量就一行一个：`DECLARE Total : INTEGER`，下一行再写下一个 |

**（b）引擎已经知道、但原来没说出口的。** 类型都算出来了，不写进提示等于让学生自己再推一遍。

| 规则 | 原来说的 | 现在说的 |
|---|---|---|
| `type.relation.incompatibleOperands` | 关系运算两侧类型不兼容 | 比较的两边类型要对得上；这里左边是 `INTEGER`，右边是 `STRING` |
| `type.arithmetic.requiresNumeric` | 算术运算需要 INTEGER 或 REAL | 算术运算两边都必须是 `INTEGER` 或 `REAL`；这里左边是 `STRING`，右边是 `INTEGER` |
| `type.condition.requiresBoolean` | 控制结构条件必须是 BOOLEAN | 条件必须是一个 `BOOLEAN`；这里是 `INTEGER`。条件通常写成一次比较，例如 `Score >= 50` |

**（c）报对了、但报在了学生用不上的位置。** 缺结束符原来一律报在文件末尾，程序一长就等于没报。现在指回那个没被闭合的开头，行号也写进文案：`IF`/`CASE`/`FOR`/`WHILE`/`REPEAT`/`PROCEDURE`/`FUNCTION`/`TYPE`/`CLASS` 九处全部改过——「第 3 行的 `IF` 没有对应的 `ENDIF`」。嵌套时指向的是真正没闭合的那一个。

**（d）原有的三条。**

| 规则 | 触发 | 说给学生的话 |
|---|---|---|
| `token.chinesePunctuation`（ID-001） | 代码里出现 `，。；：（）「」` 等全角标点 | 检测到中文标点 `，`。请切换到英文输入法，并使用英文半角符号 |
| `typo.keywordSuggestion`（TYPO-001） | 标识符与关键字 / 类型名 / 内置函数名相差一次编辑或一次相邻字母调换 | 这里的 `outpit` 可能是拼写错误。你想写 `OUTPUT` 吗 |
| `parser.output.requiresComma`（IO-002） | `OUTPUT` 后面还剩着能开启新表达式的东西 | `OUTPUT` 的多个值之间要用逗号分隔；要显示的文字要放进双引号里 |
| `parser.bindingName.cannotBeKeyword`（ID-002） | 在声明名称、`FOR` 控制变量或 `NEXT` 变量位置使用已有关键字 / 类型名 | `CLASS` 是关键字，不能作为 identifier。请换一个名称，例如 `ClassNo` |

### 3.1.1 不改的那几条

**够直接的就不要动。** `DIV 和 MOD 两侧都必须是 INTEGER` 已经把该说的都说了，再加话只是啰嗦。

`runtime.limit.outputLines`（输出行数超过上限）与 `runtime.limit.steps`（执行超过 N 步，可能存在无限循环）也不改。它们确实把「结果」当成了「原因」，但要说出真正的原因（`WHILE` 的条件变量在循环体里从没被改过）需要一套数据流分析，代价和收益不成比例；而且学生看到程序停在这里，本来就会去看循环。

### 3.2 判题时、语法完全合法（`packages/exercise/src/notes.ts`）

| 规则 | 触发 | 说给学生的话 |
|---|---|---|
| `variable-in-string` | 整条 `OUTPUT` 里只有字符串，且串里出现了已声明的变量名 | 引号里的内容会原样显示。`Name` 写在引号里就只是这几个字母本身，不会变成读进来的值 |

这一类是**语法没错、跑得起来、结果不对**的情况。`OUTPUT "name", " lives in ", "city"` 三段都是字面量，程序照做，显示的是 `name lives in city` 这几个字，不是两个变量的值——编译器无话可说，只有指导者能说。

所有这些规则都有成对的测试：`packages/language/test/guidance.test.ts`（25 项）——该报的要报，**不该报的一条都不许冒出来**，例如英文双引号里的中文标点（`OUTPUT "你好，世界。"`）必须零诊断。

### 3.3 判题失败时的差异分类（`packages/exercise/src/compare.ts`）

把「输出不符」拆成四类，各给不同的话：行数不对 / 引号里的文字写错了 / 显示的数据不对 / 漏了或多了一整块。详见 [02-CONTENT_SPEC.md](02-CONTENT_SPEC.md) 2.6。

## 4. 加一条新的，要满足什么

### 4.1 可以提前加，因为它是防护

**这一条在 1.2 版改过。** 原来写的是「每一条都必须来自真实撞到的情况」，现在不要这个限制了。

理由：指导提示是**防护**，提前布防没有坏处。真有人撞上，他得到的是一句有用的话；没人撞上，这条检查就一辈子不触发，不占学生任何注意力。等真人撞到再补，只是让第一个撞上的人白撞一次。后面发现没防住的，再补上就是了，两者不冲突。

**但禁止编造学情这条一个字没松，它管的是另一头：**

| | 在哪儿 | 什么时候说 | 判定 |
|---|---|---|---|
| 教学正文写「你可能会在这里写错」 | 课文 | **还没发生**就先说 | 禁止 |
| 检查规则说「你这里写了 `+`，接文字要用 `&`」 | 反馈 | **已经写出来了**才说 | 鼓励 |

分界不在「有没有猜」，而在**猜的时机与对象**：

- 猜「会有人这么写」→ 可以，拿它去布一道防护。猜错了没有代价，检查不触发而已。
- 猜「你会这么错」→ 不可以，那是写进课文、对着还没犯错的人说的。猜错了的代价是学生记住了一个他本来不会犯的错。

所以判断一条新规则该不该加，问的不再是「有人真撞过吗」，而是 4.2–4.6 这五条：**指得到具体位置吗、给得出正确写法吗、误报率算过吗、连锁噪音收了吗、误报测试写了吗。**

（原来的出处仍然值得记着，因为它们说明这类提示确实有人需要：全角标点与近似拼写来自使用者提出，`variable-in-string` 来自真的有人写出 `OUTPUT "name lives in asw"`，`requiresComma` 来自真的有人写出 `OUTPUT Name lives in City`。）

### 4.2 必须指得到具体的东西

行号 + 那个词。指不到具体位置的提示等于没说。

### 4.3 必须给出正确写法

`OUTPUT "Hello, ", Name` 这样的一行，比三句解释管用。

### 4.4 误报的代价要按实际概率算，不是一味保守

**故意把变量命名成 `outpit` 的人，比打错字的人少得多。** 所以拼写建议应当积极，不该因为「万一有人真想叫这个名字」就不报。

但「积极」不等于没有闸门。现在这两道都不能省：

1. **替换回去重新分析一遍。** 把猜的那个词换进源码再跑一次分析，只有错误真的变少才给建议。候选不止一个时（`inpt` 既像 `INPUT` 又像 `INT`），逐个试，**恰好剩一个能修好**才采纳；剩多个说明确实分不清，宁可不说。

   **这道闸门到底拦下了多少？** 拿十段代码量过：字面上够近的候选共 10 个，闸门拦掉 7 个，全部该拦——

   | 被拦的候选 | 为什么该拦 |
   |---|---|
   | `Dat→DATE` | 学生想写的是自己声明的 `Data`，不是类型名 |
   | `Rea→READ` / `Rea→REAL` | 两个都换不成立 |
   | `Chr→CHAR` | 换完 `OUTPUT CHAR` 照样不成立 |
   | `Case2→CASE` | 同上 |
   | `inpt→INT` | 多候选里错的那个 |
   | `Int2→INT` | 见下面第 3 条 |

   放行的三个（`outpit→OUTPUT`、`sting→STRING`、`inpt→INPUT`）都对。**没有这道闸门，误报率会从 0 升到 70%。**
2. **候选要放进它该出现的位置才算数。** 内置函数名只在后面紧跟左括号时才作为候选——`LENGHT("x")` 是在调用，`Int2` 只是个变量名。
   这一条是被打脸打出来的：`OUTPUT Int2` 一度被建议成 `OUTPUT INT`，而且**通过了第 1 道闸门**——因为引擎接受裸写的内置函数名（`OUTPUT INT` 零诊断），替换之后错误确实变少了。
   **教训：「换完之后错误变少」只是「这个建议有道理」的代理，代理会在引擎宽松的地方失灵。** 位置约束是对它的补充，不是替代。

3. **用户自己声明过的名字永远不进候选。** `Mix` 离 `MID` 只差一个字母，但它是个合法的过程名；`Whole` 离 `WHILE` 也只差一个。把对的代码说成错的，比漏报伤害大得多。

这三道闸门不冲突。实测 13 个真实打字错误——`outpit`、`oatput`、`ouput`、`outputt`、`inpt`、`inptu`、`declar`、`declaer`、`dcelare`、`whiel`、`endwihle`、`strig`、`sting`——**全部命中**，同时 `Mix` / `Whole` 这类合法命名一条都不误报。**三道闸门加起来没有让检出率付出任何代价：13/13 命中，误报 0。**

### 4.5 给出建议之后，抑制它引发的连锁错误

既然已经确认「换成这个词错误会减少」，落在同一个词上的其它错误就都是它的后果。「找不到自定义类型 `STRIGN`」和「你想写 `STRING` 吗」并排出现只是噪音——后者已经回答了前者。

### 4.6 先写误报测试，再写实现

`variable-in-string` 第一版就在 `OUTPUT "Enter the name"` 上误报了，因为提示语里正好有 `name`。这类启发式检查的边界条件比主逻辑更难想，**测试要先写**。

## 5. 还可以补什么

- **`OUTPUT Name "..." City`**（少了逗号但有引号）——目前会命中 `requiresComma`，措辞是否够贴切没验证过。
- **数组越界时指出是哪个循环跑过头**：`下标 4 超出范围 1:3` 已经够清楚，但如果能补一句「第 3 行的 `FOR` 跑到 4，数组只到 3」会更省事。需要把运行时错误和静态的循环边界对起来。
- **读未初始化变量**：文案已经改成「先用 `INPUT` 读进来，或先给它赋一个值」。更进一步的「整段代码里这个名字只出现这一次」需要数据流分析，没做。
- **引擎接受裸写的内置函数名**：`OUTPUT INT`、`OUTPUT LENGTH` 都是零诊断。这本身可能是语言层该收紧的地方（一个函数名不该能当值输出），但那是语义改动，没有顺手做。

补的时候记住第 4.1 条：**可以提前布防；但不能在课文里预告学生会怎么错。**
